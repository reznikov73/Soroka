# TASK-074 - Получатели письма, кнопка «Написать ответ», плавное перетаскивание

Дата: 2026-11-05. Версия: 0.46.28.

## 1. Получатели в данных письма

Проблема: в шапке был только отправитель, хотя писем с несколькими адресатами много.

Что выяснилось: `TO` уже запрашивался при синхронизации (`HEADER_QUERY` в `mail/imap.rs`), но отбрасывался при разборе заголовков. Поэтому дополнительный трафик почти не понадобился.

Сделано:

- В `MessageHeader` добавлены поля `to` и `cc` (`mail/imap.rs`).
- Разбор заголовков: `to` и `cc` декодируются из RFC 2047, переводы строк схлопываются в пробелы.
- В запрос заголовков добавлено `CC`.
- Схема БД: колонки `to_addrs`, `cc_addrs` в `messages`, миграция по существующему образцу (проверка через `pragma_table_info`), запись и чтение обновлены.
- Фронтенд: строка «Кому:» с чипами, первые два адреса, остальные по кнопке «+N», кнопка «Копировать»; отдельная строка «Копия:».
- Для старых писем без данных — однократная догрузка существующей командой `message_recipients` при открытии, результат кэшируется в памяти.

## 2. Кнопка «Написать ответ» в окне ответа

Проблема: рядом с «Улучшить» не было кнопки, которая пишет ответ.

Что выяснилось: команда `draft_reply` уже существует (TASK-014) и пишет ответ в стиле прошлых писем пользователя. Не хватало интерфейса в окне ответа и выбора тона.

Сделано:

- В команду `draft_reply` добавлен необязательный параметр `tone`; к промту добавляется указание тона и запрет выдумывать факты (вместо догадок — `[уточнить]`).
- В окне ответа появилась кнопка «Написать ответ» и выбор тона: Официально (по умолчанию), Кратко, Дружелюбно.
- Кнопка видна только в окне, открытом как ответ на письмо: контекст (папка, uid, тема, отправитель) передаётся через уже существующий механизм prefill.
- Пустое тело — ответ вставляется сразу. Непустое — панель «Заменить / Дополнить / Отмена».
- Во время запроса кнопка неактивна и показывает «Пишу...», ошибки выводятся тостом.

## 3. Перетаскивание окна

Проблема: окно двигалось рывками.

Причина: перетаскивание было реализовано вручную — на каждое движение указателя вызывался `setPosition`, то есть IPC-вызов в Rust на кадр.

Сделано: вместо ручного цикла вызывается нативное `startDragging()` (разрешение уже было выдано). Ручной код и неиспользуемый импорт удалены.

## Файлы

- `src/main.ts` — перетаскивание, получатели, логика кнопки ответа;
- `index.html` — блок получателей, кнопка и выбор тона, панель подтверждения;
- `src/styles.css` — стили получателей и панели;
- `src-tauri/src/mail/imap.rs`, `mail/store.rs` — поля, запрос заголовков, кэш;
- `src-tauri/src/commands/mod.rs` — параметр тона.

## Что не проверено

1. Реальная синхронизация с почтовым сервером: появятся ли `to`/`cc` у новых писем (нужен живой ящик).
2. Миграция на существующей базе пользователя: старые строки получат пустые `to_addrs`/`cc_addrs`.
3. Плавность перетаскивания: требует ручной проверки мышью.
4. Генерация ответа: требует настроенного ключа GigaChat.

## Замечание

Окно, открытое как ответ из отдельного окна чтения, получает контекст через `ReaderActionPayload` (добавлены `folder` и `uid`). Если письмо открыто из папки, недоступной по IMAP на момент генерации, кнопка вернёт ошибку с текстом — это ожидаемо.
