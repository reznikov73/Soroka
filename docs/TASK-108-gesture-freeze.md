# TASK-108 — Жёсткая заморозка WebView2 на время системного жеста ресайза

Дата: 2026-11-18. Версия: 0.46.57. База: `c334323` (0.46.56, TASK-107).

## Постановка

После TASK-107 (полностью системные окна, в цикле ресайза ноль нашего кода) владелец сообщил: «рамка окна двигается, внутренние элементы тормозят». Это ключевой эксперимент: стоимость не в нашей шапке и не в наших командах — она в перестройке и отрисовке DOM внутри WebView2 на каждый шаг жеста. Поднять эту скорость нельзя, пока вебвью виден во время ресайза.

Вопрос владельца: «может, всё переделать на Win32?» Полный rewrite — это месяцы и потеря всего фронтенда (9k строк TS, темы, FTS-поиск, AI, календарь). Приём ниже даёт Win32-скорость самого жеста без переписывания: тяжёлая раскладка делается один раз — после жеста.

## Решение

**Ghost resize** — тот же эффект, что у Windows при выключенной опции «Отображать содержимое окна при перетаскивании»:

1. Новый модуль `src-tauri/src/gesture_freeze.rs` сабклассирует окно (свой `SUBCLASS_ID`, не задевает сабклассы wry/tao).
2. `WM_ENTERSIZEMOVE` — ставим флаг «идёт модальный цикл».
3. Первый `WM_SIZE` внутри цикла (значит, это именно ресайз, а не перетаскивание) — прячем дочернее окно WebView2 (`EnumChildWindows` → класс `Chrome_WidgetWin_1` → `ShowWindow(SW_HIDE)`). Дальше wry обновляет bounds уже скрытого окна — это дёшево.
4. `WM_ERASEBKGND` — родитель закрашивается кистью цвета темы (`--bg-app`: тёмная `#1c1e24`, светлая `#f7f8fa`), без белых вспышек.
5. `WM_EXITSIZEMOVE` — возвращаем вебвью (`SW_SHOW`), он делает одну раскладку финального размера; фокус возвращается туда, где был (`GetFocus`/`SetFocus`).

Чего здесь **нет** — и почему: дросселя WM_SIZE (именно он замедлил 0.46.54), IPC в цикле, `eval()` из оконной процедуры (замедлил старт жеста в 0.46.54 по разбору TASK-106). Заморозка не «режет» события — она убирает из кадра саму тяжёлую работу.

Перетаскивание без изменения размера содержимое не прячет: там раскладки нет, окно и так едет быстро. Максимизация/восстановление и `Win+стрелки` идут вне модального цикла — не затронуты.

Применение: команда `apply_gesture_freeze(bg)` вызывается один раз из JS после `initTheme()` в каждом окне (главное, чтение, настройки, редактор — один вызов до ветвления загрузки). Цвет фона передаётся из JS по активной теме. Повторные вызовы игнорируются (защита от утечки состояния), ошибки безопасны — окно остаётся просто системным.

## Сделано

- `src-tauri/src/gesture_freeze.rs` — новый модуль (сабкласс, поиск WebView2-ребёнка, кисть, фокус; освобождение в `WM_DESTROY`).
- `src-tauri/src/commands/mod.rs` — команда `apply_gesture_freeze` (парсинг `#RRGGBB`, тёмный по умолчанию, заглушка не-Windows).
- `src-tauri/src/lib.rs` — модуль + регистрация команды.
- `src/main.ts` — `applyGestureFreeze()` и вызов после `initTheme()` (+15 строк).
- Версии: `tauri.conf.json`, `Cargo.toml`, `Cargo.lock`, `package.json` → 0.46.57.

### Осталось (Windows, у владельца)

- `cargo clippy --all-targets -- -D warnings`, `cargo test`, `npm run tauri build`.
- Живая проверка: тянуть край главного окна — содержимое исчезает, окно идёт за курсором мгновенно, на отпускании возвращается; то же в окнах чтения/настроек/редактора; фокус (курсор в поле письма) сохраняется после жеста; тёмная и светлая темы — фон под заморозкой правильный.
- Отдельно, для понимания среды: открыть в Edge на этой же машине тяжёлую страницу и потянуть край окна Edge. Если Edge тоже отстаёт — дело в среде (GPU-драйвер, RDP-сессия), и никакой фронтенд-код это не лечит.

## План Б

Если хочется видеть содержимое во время ресайза ценой скорости — заморозку можно ослабить: прятать не весь вебвью, а только список писем (`content-visibility` из TASK-106, но уже на системном жесте). Если же и заморозка не даст мгновенной рамки — значит, узкое место в самой очереди сообщений окна (например, антивирус или RDP), это проверяется утилитой Spy++ по задержке `WM_SIZE`.
