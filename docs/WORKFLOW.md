# Правила работы над POS Mail (soroka)

Зафиксировано: 2026-11-03. Этот файл — точка входа, чтобы продолжить работу в новой сессии.

## Где что лежит

| Файл | Назначение |
|---|---|
| `docs/WORKFLOW.md` | правила нашего рабочего цикла (этот файл) |
| `docs/TASK-NNN-<имя>.md` | постановка задачи, принятые решения, что изменено, как проверено |
| `docs/screenshots/` | снимки интерфейса для README |
| `docs/build-log.txt` | вывод последней сборки (в `.gitignore`, в репозиторий не попадает) |

Все служебные материалы — инструкции, правила, ТЗ, постановки задач, отчёты — пишутся **только в `docs/`**. Папка `tasks/`, упомянутая в README, не используется.

## 1. Перед выполнением задачи

1. Пересказать, как понята задача: что меняем, где, чего не трогаем.
2. Задать уточняющие вопросы, если есть развилки.
3. Начать кодировать только после явного разрешения пользователя.

## 2. После изменений — полный цикл

1. Правки кода.
2. Версия: patch (`0.46.5 → 0.46.6`) в `src-tauri/tauri.conf.json`; `scripts/sync-version.ps1` разносит её в `Cargo.toml` и `package.json`; новый раздел в `CHANGELOG.md`.
3. Сборка: `npm run tauri build` → `src-tauri/target/release/POSmail.exe` и `src-tauri/target/release/bundle/nsis/POS Mail_<версия>_x64-setup.exe`. Сборка идёт фоновым процессом, вывод пишется в `docs/build-log.txt`; наличие и размер обоих файлов проверяются по логу.
4. Коммит: `fix: vX.Y.Z — суть изменения (TASK-NNN)`.
5. Пуш: `git push origin main`, без PR.

Если сборка или проверки падают — не коммитить и не пушить: показать ошибку и ждать решения.

## 3. Обрывы связи и чекпоинты

Баннер «Ресурсы модели сейчас перегружены» означает, что запуск оборван сервисом модели: локально работа не продолжается. Поэтому работа строится так, чтобы обрыв стоил максимум одного шага.

1. Длинные операции (сборка, тесты) — фоновым процессом с записью вывода в `docs/build-log.txt` (файл в `.gitignore`). После обрыва результат проверяется по логу, а не повторной сборкой вслепую.
2. После каждого логического шага — чекпоинт: коммит (и пуш, если шаг завершён) + обновление файла задачи.
3. Файл задачи `docs/TASK-NNN-<имя>.md` ведётся по шаблону:
   - `## Постановка` — что просили;
   - `## Решения` — что выбрали и почему;
   - `## Сделано` — изменённые файлы;
   - `## Проверено` — сборка, тесты, артефакты;
   - `## Осталось` — следующий шаг, если работа прервана.
4. Команда «продолжай» после обрыва: читаю `docs/WORKFLOW.md`, последний `docs/TASK-*.md`, `docs/build-log.txt` и `git log` — и продолжаю с записанного шага, не переспрашивая.

1. Прочитать `docs/WORKFLOW.md`.
2. Посмотреть последний файл `docs/TASK-*.md`.
3. `git log --oneline -5`, `git status` и `docs/build-log.txt` — понять, на чём остановились.
4. Дальше — по разделу 1.
